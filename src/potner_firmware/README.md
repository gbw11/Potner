# potner_firmware — ESP32 저수준 컨트롤러

젯슨이 못 하는 실시간 작업만 담당합니다.

| 담당 | 이유 |
|---|---|
| 엔코더 쿼드러처 디코딩 | 초당 약 2,930카운트 × 2. 리눅스 파이썬으로는 카운트를 흘립니다 |
| 바퀴 속도 PID (100Hz) | 주기가 흔들리면 안 되는 제어 루프 |
| 20kHz PWM 생성 | 가청 대역 밖이라 조용합니다 |
| 워치독 정지 | 젯슨이 죽어도 로봇이 계속 달리지 않게 |

## ⚠️ 젯슨 전원 켤 때마다 필요한 작업 (CH340 드라이버)

지금 쓰는 ESP32 DevKit V1 보드는 USB-시리얼 브리지로 **CH340(벤더 1a86:7523)**을
씁니다. 그런데 이 Jetson의 Tegra 커널(`5.15.148-tegra`)에는 `ch341` 드라이버가
빠져 있어서, 커널 모듈을 직접 빌드해서 넣어야 합니다. **이 모듈은 재부팅하면
날아가므로, 부팅할 때마다 다시 로드해야 합니다.**

```bash
sudo modprobe usbserial
sudo insmod ~/ch341-build/ch341.ko
```

그다음 USB 케이블을 뽑았다 다시 꽂고:

```bash
ls -l /dev/ttyUSB* /dev/ttyACM* 2>/dev/null
```

`/dev/ttyUSB0`가 잡히면 정상입니다 (ESP32가 아니라 CH340 칩 자체가 이 이름으로
잡힙니다 — LiDAR의 CP2102와는 별개 장치입니다).

`~/ch341-build/ch341.ko`가 없으면 처음부터 빌드해야 합니다:

```bash
mkdir -p ~/ch341-build && cd ~/ch341-build
wget -O ch341.c https://raw.githubusercontent.com/torvalds/linux/v5.15/drivers/usb/serial/ch341.c
printf 'obj-m += ch341.o\nall:\n\tmake -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules\nclean:\n\tmake -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean\n' > Makefile
make
```

**`brltty` 패키지가 깔려 있으면 반드시 제거하세요** — 점자 단말기 드라이버인데
udev 규칙이 CH340을 자기 것으로 가로채서, 드라이버가 붙자마자 바로 떼어내 버립니다.

```bash
sudo apt remove --purge -y brltty
```

## 배선

### ESP32 → BTS7960 (모터 드라이버 2개)

| ESP32 핀 | 연결 |
|---|---|
| GPIO 25 | 좌 BTS7960 RPWM |
| GPIO 26 | 좌 BTS7960 LPWM |
| GPIO 32 | 우 BTS7960 RPWM |
| GPIO 33 | 우 BTS7960 LPWM |
| 3.3V | 양쪽 BTS7960 의 R_EN, L_EN (항상 활성) |

### 엔코더 → ESP32 (3.3V 직결, 레벨 시프터 불필요 — 실측 확인)

FIT0403 엔코더는 **VCC를 3.3V로 넣어도 정상 동작**합니다. 실기에서 손으로
축을 돌려 A/B 출력이 0~3.3V로 잘 스위칭되는 것과, PWM 구동 중 틱 카운트가
정상적으로 올라가는 것까지 확인했습니다. 레벨 시프터나 저항 분압 없이
직결하면 됩니다.

| ESP32 핀 | 연결 |
|---|---|
| GPIO 34 | 좌 엔코더 A (직결) |
| GPIO 35 | 좌 엔코더 B (직결) |
| GPIO 36 | 우 엔코더 A (직결) |
| GPIO 39 | 우 엔코더 B (직결) |

엔코더 VCC/GND도 ESP32 3.3V/GND에 연결합니다.

GPIO 34~39를 고른 이유는 **입력 전용 핀**이라서입니다. 출력으로는 못 쓰는
핀이니 엔코더에 배정하면 출력 가능한 핀을 아낄 수 있습니다.

### 절대 쓰면 안 되는 핀

- **GPIO 0, 2, 12, 15** — 부팅 스트래핑 핀. 여기에 뭘 물리면 ESP32가 안 켜집니다
- **GPIO 6~11** — 내부 플래시 전용

### ⚠️ 전원 접지

3S(모터)와 4S(젯슨) 배터리를 따로 쓰므로 **GND 한 가닥을 반드시 서로
연결**해야 합니다. ESP32는 젯슨 USB에서 전기를 받고 BTS7960은 3S에서
받는데, 기준점이 다르면 PWM 신호를 못 알아듣습니다. 플러스는 절대 섞지
마세요.

여기서 "GND"는 BMS에 그렇게 라벨링된 별도 핀이 아니라, **3S 팩의 (−)
방전 리드선**을 가리킵니다. 이 리드선을 BTS7960 `B−`와 4S 팩 (−) 양쪽으로
분기해서 연결하면 됩니다.

## 시리얼 프로토콜

`src/potner_base/potner_base/serial_protocol.py` 와 **반드시 일치**해야
합니다. 한쪽만 고치면 조용히 오작동합니다.

```
젯슨 -> ESP32
    V,<좌 m/s>,<우 m/s>*<체크섬>\n
    S*<체크섬>\n

ESP32 -> 젯슨
    O,<좌틱>,<우틱>,<좌범퍼mm>,<우범퍼mm>,<millis>*<체크섬>\n
```

체크섬은 `*` 앞까지 모든 문자의 XOR을 2자리 16진수로 적습니다.

## 튜닝이 필요한 값

`src/main.cpp` 상단에 모여 있습니다.

- `WHEEL_DIAMETER_M` — 조립 후 실측
- `KP`, `KI`, `KD` — 바퀴가 떨리면 KP를 낮추고, 목표 속도에 못 미치면 KI를 올립니다
- `MIN_DRIVE_DUTY` — 비영점 목표가 정지 마찰을 이기기 위한 PWM feed-forward
- `MAX_WHEEL_MPS` — 안전 상한

FIT0403 사양의 출력축 분해능은 1440 pulse/rev입니다. 이 펌웨어는
`attachFullQuad()`로 각 pulse의 네 edge를 모두 세므로
`COUNTS_PER_REV = 5760`을 사용합니다. Jetson의 `counts_per_rev`도 반드시
5760으로 맞춰야 합니다.

실제 로봇에서 각 바퀴를 전진 방향으로 손으로 돌려 `/odom`을 측정한 결과,
왼쪽 엔코더만 ROS 전진 부호와 반대이고 오른쪽은 일치했습니다. 따라서 누적
엔코더 카운트에는 다음 정수 부호를 적용합니다.

- `LEFT_ENCODER_SIGN = -1`
- `RIGHT_ENCODER_SIGN = +1`

동일한 측정 과정과 설치된 BTS7960 출력 방향을 기준으로 최종 PWM에는 다음
부호를 적용합니다.

- `LEFT_MOTOR_OUTPUT_SIGN = +1.0f`
- `RIGHT_MOTOR_OUTPUT_SIGN = -1.0f`

정규화된 엔코더 카운트는 PID와 Jetson 오도메트리 전송에 똑같이 사용하므로
Jetson에서 다시 부호를 반전하면 안 됩니다.

`S` 정지 프레임, `V,0,0` 속도 프레임 또는 500ms 명령 watchdog이 발생하면
펌웨어는 PID를 비활성화하고 양쪽 PWM을 0으로 유지합니다. 이후 유효한 0이
아닌 속도 프레임이 들어와야만 PID가 다시 활성화됩니다. 따라서 정지 상태에서
바퀴를 손으로 움직여도 PID가 모터를 다시 구동하지 않습니다.

속도 프레임은 좌우 값이 모두 완전한 유한 실수인지 확인합니다. 필드가 더 있거나
숫자가 아닌 값, `NaN`, 무한대가 포함된 프레임은 주행 상태와 watchdog 시간을
변경하지 않고 버립니다.

실기에서 `0.03m/s`는 PID duty가 약 0.16까지 쌓인 뒤에야 바퀴가 조금
움직였고 `0.08m/s`에서는 양쪽이 정상 기동했습니다. 따라서 비영점 목표에는
`MIN_DRIVE_DUTY = 0.16f`를 목표 방향으로 더합니다. 이 값은 고정 PWM 명령이
아니라 feed-forward이므로, 실제 속도가 목표보다 높으면 PID feedback이 이를
감산합니다. 목표가 0인 바퀴는 이전 적분값을 지우고 PWM 0을 반환합니다.
목표 방향이 반대로 바뀔 때도 바퀴별 적분과 이전 오차를 먼저 초기화하므로,
장애물에 걸려 쌓인 적분값이 새 명령과 반대 방향으로 모터를 밀지 않습니다.
전체 정지 경로는 계속 PWM 0을 직접 출력합니다.

**좌우 편차 테스트 시 주의**: `WATCHDOG_TIMEOUT_MS = 500` 때문에 `V,...` 명령을
한 번만 보내면 0.5초 후 자동 정지합니다. 이 상태로 좌우 카운트를 비교하면
가속 구간(과도 상태)만 보게 돼서 실제보다 훨씬 큰 편차(13~49%)로 착시가
생깁니다. 명령을 0.2초 간격으로 반복 전송해서 몇 초간 정상 상태(steady
state)에 도달시킨 뒤 비교해야 정확합니다 — 이렇게 재보니 `KI=1600`에서
좌우 편차는 약 4~5% 수준으로, 정상적인 하드웨어 개체차 범위입니다.

## 첫 동작 확인 순서

**바퀴를 공중에 띄운 채로** 시작하세요. 바닥에 놓고 하면 책상에서 떨어집니다.

1. `pio run --target upload` 로 업로드
2. `pio device monitor` 로 `O,...` 프레임이 30Hz로 올라오는지 확인
3. 손으로 바퀴를 굴려서 틱 카운트가 변하는지 확인 — 안 변하면 배선 문제
4. 왼쪽과 오른쪽 바퀴를 각각 앞으로 굴렸을 때 Jetson으로 전송되는 정규화
   카운트가 모두 **증가**하는지 확인. 원시 왼쪽 카운트 반전은 펌웨어에서
   처리하므로 엔코더 A/B 배선을 바꾸지 마세요
5. 시리얼 모니터에 `V,0.05,0.05*` + 체크섬을 직접 입력해 바퀴가 도는지 확인
6. ROS에서 `0.03m/s` 전진 명령을 4초 보내 양쪽이 지연 없이 전진하는지 확인
7. Nav2 최대 회전 명령인 `+0.35rad/s`에서 왼쪽은 후진, 오른쪽은 전진하고
   `/odom`의 `angular.z`가 양수인지 확인
